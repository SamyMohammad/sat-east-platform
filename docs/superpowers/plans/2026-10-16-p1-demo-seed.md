# P1 Part 1 — Staging Demo Seed Implementation Plan

> **For agentic workers:** Use superpowers:subagent-driven-development. An `implementer` agent writes the SQL, scripts and CI. The seed checks are SQL assertion scripts, not `*_test.dart`, so no test-writer is needed; each content task still gets a reviewer. Steps use checkbox syntax.

**Goal:** Put a demo SAT course on staging, re-applied on every main deploy. It has 3 topics with 12 practice and 12 quiz questions each, keys in `private.question_keys`, and every student auto-enrolled. Parts 2–5 of the vertical slice run against this data.

**Architecture:**
- Idempotent SQL files live in `supabase/seeds/demo/`. They use fixed UUIDs and upsert.
- A seed-only helper, `private.demo_upsert_question(...)`, keeps the content files compact.
- A seed-only trigger enrols new students.
- CI applies the files to staging after `supabase db push` with `supabase db query --linked --file`, through the Management API, so no new secrets are needed.
- The files are not in `config.toml` `sql_paths`, so the local and CI pgTAP database stays as the existing tests expect.
- CI validates the seed in the `db` job: it applies the files twice to the local stack, then runs an assertion script.

**Tech Stack:** Postgres 15 (Supabase), Supabase CLI 2.117.0, GitHub Actions, PowerShell scripts.

**Spec:** `docs/superpowers/specs/2026-10-16-p1-slice-demo-seed-design.md` (12abeed), with the deltas below.

## Spec deltas (found while planning, 2026-10-16)
1. **Key shapes** come from `docs/06-data-model.md:148` and `private.grade_spr` (`supabase/migrations/20261007015636_grd02_spr_grader.sql:54-90`):
   - MCQ: `{"choice":"B"}`.
   - SPR: `{"accepted":["2/3","0.666","0.667"],"tolerance":0}`. Every accepted string must pass `private.spr_parse(…, false)`: an integer, a decimal or `a/b`, an optional leading `-`, and no spaces. Student input is at most 5 characters, or 6 with `-`.
2. **Delivery is not `--include-seed`.** In CLI seed tracking, a changed ("dirty") seed file only refreshes its hash and is never re-executed. Content edits would therefore never reach staging. Instead, CI runs `supabase db query --linked --file <f>` for each file in `supabase/seeds/demo/` (sorted) on every main deploy. The files are idempotent.
   - Task 1 confirms that `db query --linked --file` exists in CLI 2.117.0 and executes a multi-statement file in one call.
   - Fallback if it does not: `psql` with the pooler URL that `supabase link` writes to `supabase/.temp/pooler-url`, plus the existing `STAGING_DB_PASSWORD`.
3. **The local/CI test database does not load the demo seed.** Seven existing test files insert their own `SAT` course (`courses.code` is unique), and the auto-enrol trigger would change their enrolment rows. So `config.toml` `sql_paths` stays `["./seed.sql"]`.
   - Local manual use goes through a new `scripts/db-seed-demo.ps1`.
   - CI validates the seed separately (Task 4).
4. **The demo course uses `code = 'SAT'`** (code is unique, one course per code). When the real SAT course arrives on staging, the demo course is renamed or removed. That is a note in the seed header and STATUS Open, not code.
5. **The question count is 72, not 108.** 3 topics × (12 practice + 12 quiz) = 72; the spec's "108" was a miscount.

## Global Constraints
- Every statement is idempotent: `insert … on conflict (…) do update` / `do nothing`, `create or replace function`, `drop trigger if exists` then `create trigger`. Running all files twice leaves every row count unchanged.
- Use fixed UUIDs only, written literally (never computed in SQL). The prefix is `00000000-0000-4000-8de0-`, followed by a 12-digit suffix:
  - course `000000000001`;
  - unit `000000000002`;
  - topics `000000000011`, `000000000012` and `000000000013`;
  - subtopics `000000000021`, `000000000022` and `000000000023`;
  - skills `000000000031` to `000000000036`;
  - questions `0000000TPNNN`, where T is the topic (1–3), P is 1 for practice or 2 for quiz, and NNN is 001–012.

  Example: topic 1, quiz question 7 is `00000000-0000-4000-8de0-000000012007`.
- Functions are `security definer`, `set search_path = ''`, in schema `private`, with no grants to `anon`/`authenticated`. CLAUDE.md rule 9 applies only to RPCs, and these are not RPCs.
- Never touch `supabase/migrations/`. The demo data must never be in a migration.
- Content:
  - original, SAT-style algebra, English stems;
  - `source = 'demo'`, `status = 'published'`, `pool` per file section;
  - LaTeX in `\( … \)` (MathText);
  - explanations in Markdown, at least 2 per topic with an Arabic paragraph;
  - no College Board text.
- Do not use PowerShell `Get-Content | Set-Content` on UTF-8 files. Use the Write/Edit tools.
- Never commit `.codex/` or `.impeccable/`. They are staged and unrelated, so use `git commit -- <paths>`.

## Review Focus
1. **Idempotence:** a second run of every file must not duplicate rows or fail, including the trigger and helper creation. → Task 4 script.
2. **SPR keys the grader rejects:** an accepted string with a space, `+`, more than 5 characters, or `.5`. Check `spr_parse` for what it accepts. → Task 4 asserts `private.grade_spr(<each accepted>, key) = true` for every SPR key.
3. **MCQ key not among its choices**, or a question without exactly 4 choices. → Task 4.
4. **Trigger on non-students:** a profile later updated to `teacher` stays enrolled, which is harmless. The trigger must not fail when the demo course is missing; prod never has this trigger anyway. → Task 1 (guard with `if exists`).
5. **Staging apply failure must fail the deploy step loudly,** not silently skip. → Task 1 CI step uses `set -euo pipefail`.

## Task 1 — Structure, helper, enrolment, delivery

`00_structure.sql`:
- **Header comment:** what the file is, staging and local only, never prod, idempotent, and the course-code note (delta 4).
- **Course:**
  - `code 'SAT'`, `title 'SAT Math (Demo)'`, `slug 'sat-demo'`, `is_published true`, `description 'Demo content for the staging vertical slice.'`;
  - `on conflict (id) do update set title, slug, is_published, description`.
- **Unit:** "Algebra (Demo)".
- **Topics:** sort 1–3, slugs `linear-equations`, `linear-inequalities`, `systems-of-equations`, all published. Topic 1 has `is_free_preview = true`.
- **Subtopics:** one per topic, with the same title.
- **Skills:** codes `DEMO.LE.SOLVE`, `DEMO.LE.MODEL`, `DEMO.LI.SOLVE`, `DEMO.LI.GRAPH`, `DEMO.SYS.SOLVE`, `DEMO.SYS.MODEL`, with domain `'Algebra'` and `course_scope '{SAT}'`. Link two to each subtopic.
- **`private.demo_upsert_question`:**

  ```sql
  private.demo_upsert_question(
    p_id uuid, p_topic uuid, p_subtopic uuid, p_pool public.question_pool,
    p_type public.question_type, p_difficulty public.difficulty,
    p_stem text, p_hint text, p_choices jsonb,   -- {"A":"…","B":"…","C":"…","D":"…"} or null for SPR
    p_key jsonb, p_explanation text, p_misconceptions jsonb, p_skill_codes text[]
  ) returns void
  ```

  It does the following:
  - Upserts `questions`, with `external_ref = 'demo-' || p_id`, `source 'demo'`, `status 'published'`.
  - Deletes and re-inserts `question_choices` for that question, then upserts `question_courses` (the demo course) and `question_skills` (by code).
  - Upserts `private.question_keys`: `correct_answer = p_key`, explanation, misconceptions, `solved_by 'teacher'`.
  - Raises an exception if:
    - an MCQ has keys other than exactly A–D;
    - an MCQ key `choice` is not in A–D;
    - an SPR question has non-null `p_choices`.
- **Enrol existing students:**

  ```sql
  insert into public.enrollments (user_id, course_id, status, expires_at)
  select id, '<course>', 'active', now() + interval '1 year'
  from public.profiles where role = 'student'
  on conflict (user_id, course_id) do nothing;
  ```

- **Trigger:**
  - `private.demo_enroll_new_student()` runs `after insert on public.profiles for each row`, and only when `new.role = 'student'` and the demo course exists. It inserts the same enrolment with `on conflict do nothing`.
  - It is created with `create or replace function` followed by `drop trigger if exists demo_enroll_new_student on public.profiles; create trigger …`.

## Task 2 — Topic 1 content (Linear equations, 24 questions)

`10_topic1_linear_equations.sql`: 24 `select private.demo_upsert_question(...)` calls, laid out as:
- **Practice** (suffixes `000000011001`–`000000011012`): 9 MCQ + 3 SPR, difficulty 4 E / 5 M / 3 H, each with a `hint`.
- **Quiz** (suffixes `000000012001`–`000000012012`): 9 MCQ + 3 SPR, the same difficulty mix. `hint` is null for quiz items.

Content rules:
- Each MCQ has 4 distinct plausible choices, and the distractors come from real mistakes, such as a sign error or dividing before subtracting.
- About half of the MCQs carry `misconceptions` for 1–2 wrong labels, for example `{"A":"You subtracted 7 instead of adding it."}`.
- SPR answers are fractions or decimals that pass `spr_parse`. Include every accepted form, for example `["7/2","3.5"]`, and for repeating decimals both the truncated and the rounded 4-character forms, for example `["2/3",".666"]` only if `spr_parse` accepts a leading dot. Check this, and otherwise use `"0.666","0.667"`.
- At least 2 explanations end with an Arabic paragraph.

## Task 4 — Seed check script, CI validation, docs

`supabase/seeds/demo/check.sql` is a single `do $$ … $$` block. It raises an exception with a clear message on any violation and ends with `raise notice 'demo seed OK'`. It checks:
1. 1 demo course, 3 published topics, 3 subtopics, 6 skills.
2. Per topic: 12 practice and 12 quiz questions, all `published` with `source = 'demo'`.
3. Every demo question has exactly 1 `private.question_keys` row and 1 `question_courses` row for the demo course.
4. Every MCQ has exactly 4 choices labelled A–D, and its key is `{"choice": X}` with X among those labels.
5. Every SPR key has `accepted` as a non-empty array, and for every accepted string `private.grade_spr(s, key)` is true. This is Review Focus 2.
6. At least 6 explanations contain Arabic, matching `~ '[؀-ۿ]'`.
7. **The trigger works:**
   - In a sub-block, insert a fake `auth.users` row the same way `supabase/tests/000_setup_test_helpers.test.sql:49-64` does, so `handle_new_user` creates the profile.
   - Assert the demo enrolment exists.
   - Then delete the auth user. The cascade removes the profile and the enrolment.
   - The check must leave no residue.
8. Every existing student profile has a demo enrolment.
