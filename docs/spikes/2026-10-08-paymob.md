# Spike findings: Paymob checkout + HMAC webhook (ADR-003)

Date: 2026-10-08 · docs/15 §1 row 8 · Design: `docs/superpowers/specs/2026-10-08-adr003-paymob-spike-design.md`
Code: `spikes/paymob/` (runbook in its README).

## Verdict
**The flow works against a mock Paymob.** It covers server-side pricing, checkout redirect, a
declined attempt, a retry, the signed webhook, one enrolment and the return page, plus 16 Deno
tests and a browser run. Our HMAC matches an independent implementation (the `@m-nasser-m/paymob-sdk-eg`
source) on webhook and redirect payloads, and tampering is detected.
**Live Paymob test mode is not run yet.** Paymob is unreachable from the development sandbox.
It needs the developer's test account and machine (README part B). Paymob stays the right gateway.
Nothing found blocks it.

## Findings that change the plan
1. **Find the order by the signed Paymob order id, never by `merchant_order_id` /
   `special_reference`.** The HMAC does not cover those fields. Someone with one genuine signed
   callback for their own cheap payment could swap `merchant_order_id` and pay for another
   pending order. Covered by a test.
   **→ PAY story:** store `orders.gateway_order_id` at checkout, and match the webhook on it +
   `amount_cents` + `currency` (all three are signed).
2. **A declined card must not close the order.** Paymob's checkout lets the student retry on the
   same order. If the first decline marked the order `failed`, a later successful charge would
   find no pending order, and the student would pay and not be enrolled. A decline now leaves
   the order `pending`, and the reconciliation cron (docs/07 §7) closes stale ones.
   **→ docs/07 §7:** add this rule.
3. **One order can have several transactions.** `orders.gateway_txn_id unique` holds the
   successful one only. For idempotency on *every* delivery (declines and duplicates included),
   the PAY story should add `private.payment_events(txn_id pk, order_id, success, received_at)`
   (`insert … on conflict do nothing`) instead of relying on the single column. A second
   *successful* charge on a paid order is logged as `already_paid`. That is a double payment,
   and the teacher refunds it (PAY-11).
4. **The redirect never enrols.** Its HMAC is valid UX information, but the webhook is the only
   source of truth (PAY-03). The return page polls until the enrolment exists (realtime in the
   app). That meets "sees the course within 10 s" when the webhook is on time.
5. **`payment-webhook` needs `verify_jwt = false`** (Paymob sends no Supabase JWT), like the `/v/*`
   video routes. The HMAC is its only auth, so it must run before anything else, and a failure
   logs only the transaction id, no payload or PII.
6. **Coupon `used_count` must be checked and incremented atomically when the payment lands**, not at
   checkout. Otherwise abandoned checkouts burn uses, and two parallel payments can pass
   `max_uses`. In SQL that is one `update coupons … where used_count < max_uses returning`.

## Smaller notes
- Paymob API used: `POST /v1/intention/` (`Authorization: Token <secret>`), Unified Checkout
  `…/unifiedcheckout/?publicKey&clientSecret` (client secret valid about 1 h). Billing data
  (name, phone, email) is required, so the PAY story takes it from `profiles` (AUTH-02).
- The Paymob order id may arrive as `intention_order_id` or `payment_keys[0].order_id`. The
  client accepts both, and the live run confirms which one.
- Return page and server must share an origin (or use CORS). In dev, open the tunnel URL.
- Secret key and HMAC secret are server env only. The browser only ever sees the public key,
  inside the checkout URL.
- Webhook errors from Paymob's side (500, timeouts) are retried by Paymob. Our handler returns
  200 for every signed, well-formed event, so retries happen only on real failures.
